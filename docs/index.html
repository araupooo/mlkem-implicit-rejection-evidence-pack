ML-KEM Implicit-Rejection Evidence — Findings

Pinned builds: liboqs 0.16.0, reference (OQS_OPT_TARGET=generic) and optimized (OQS_OPT_TARGET=auto, AVX2). Parameter sets: ML-KEM-512, ML-KEM-768, ML-KEM-1024. Machine: Intel Xeon Platinum 8321HC @ 1.40 GHz, 4 vCPU, Ubuntu 24.04. Methodology: docs/methodology.md. Claims → evidence: docs/evidence-index.md. All numbers are from the unedited logs in outputs/.

Headline result

PASS — no deviation from FIPS 203 §7.3 found in either pinned build. 1,476 invalid-ciphertext decapsulations (246 per parameter set × 3 sets × 2 builds) all returned a deterministic 32-byte fallback secret, never an error, never the valid shared secret. Fallback values are bit-identical across the two builds. The re-encryption check was observed directly for ML-KEM-768: 33 of 46 single-bit-flipped ciphertexts decrypt to the same message as the valid ciphertext, yet decapsulation returns the fallback — the rejection comes solely from the re-encryption comparison.

Reading the table: the largest median gap is 79 ns (0.04%, ML-KEM-1024 reference, interleaved) — far below the noise floor. Means and standard deviations are dominated by occasional VM scheduling spikes (maxima up to ~68 ms); the medians are the robust comparison. Noise disclosure: this timing run executed concurrently with the clean-reproduction build (two liboqs builds competing for the same 4 vCPUs), which inflates the outlier tail. An earlier quiet-machine run gave medians within 1% of these values. Conclusion: no valid-vs-invalid timing difference is detectable above the noise floor; this is not a proof that no sub-noise-floor difference exists.

Limitations

  • L1 — Empirical only: fallback pseudorandomness is checked by distinctness over 246 inputs per parameter set and determinism over two runs, not proven; no statistical test suite (e.g. NIST SP 800-22) was run on fallback outputs.
  • L2 — Timing noise: single shared virtual machine; the shipped timing run competed with a concurrent build. Differences below the noise floor are reported as not detectable, not proven absent.
  • L3 — Constant-time by inspection: the constant-time comparison (mlk_ct_memcmp) and move (mlk_ct_cmov_zero) are verified by code inspection of the pinned source, not by a side-channel measurement.
  • L4 — Observation scope: the re-encryption observation covers ML-KEM-768 reference sources only; 512/1024 and the AVX2 path are covered by the public-API battery and cross-build fallback equality.
  • L5 — Length inputs: truncated/malformed-length ciphertexts cannot be passed through the public API and were not tested.
